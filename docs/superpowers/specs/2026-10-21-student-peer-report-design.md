# นักศึกษารายงานเพื่อน Lab Boy (Peer Report) — Design

วันที่: 2026-10-21 · สถานะ: รออนุมัติ (ผ่าน builder check แล้ว)

**นับเป็น blacklist** = รายงานสถานะ `CONFIRMED` (อุทธรณ์สำเร็จ → `NOT_SUBSTANTIATED` → ไม่นับ)

## เจตนา (ทำไม)

ระบบรายงานเดิม (`labassist-backend/reports`) ให้ **อาจารย์** เขียนรายงาน Lab Boy แล้ว **เจ้าหน้าที่** ตรวจ เจ้าของโปรเจกต์ต้องการเปลี่ยนเป็น: **Lab Boy รายงานเพื่อน Lab Boy ในวิชาเดียวกัน** และ **อาจารย์ผู้สอนวิชานั้นเป็นคน "ลงดาบ"** คือตัดสินว่าจะให้ blacklist หรือไม่ คนที่โดนรายงานต้องไม่มีทางรู้ว่าใครรายงาน

## สิ่งที่เจ้าของตัดสินแล้ว

1. **ผู้รายงาน = นักศึกษาเท่านั้น** ตัดความสามารถที่อาจารย์เขียนรายงานเองออกทั้งหมด (UI + API)
2. หน้า `/student/reports` แสดง **รายวิชาที่นักศึกษาเป็น Lab Boy** (ใบสมัคร `accepted`) — ปุ่ม "ดูรายชื่อ Lab Boy" → รายชื่อ Lab Boy คนอื่นในวิชานั้น (**ไม่มีชื่อตัวเอง**) → ปุ่ม "รายงาน" → popup ฟอร์มแบบเดียวกับของอาจารย์เดิม (วันที่เกิดเหตุ, ประเภท, รายละเอียด, ผลกระทบ, แนบหลักฐาน)
3. **ปุ่มรายงานมีได้เมื่อเจ้าหน้าที่ยืนยันตารางปฏิบัติงานของวิชานั้นแล้วเท่านั้น** (`posting.lab_boy_schedule_confirmed = true` และ posting active)
4. **โควตา: นักศึกษา 1 คนรายงานได้รวมไม่เกิน 3 ครั้งต่อ 1 วิชาที่ตนเป็น Lab Boy** (นับรวมทุกคนที่รายงานในวิชานั้น ไม่ใช่ต่อคนที่โดนรายงาน)
5. **ความลับผู้รายงาน**: คนโดนรายงานต้องไม่รู้เด็ดขาดว่าใครรายงาน — ทุกจุดที่เขาเห็น (หน้ารายงาน, แจ้งเตือน, ประวัติสถานะ, หลักฐาน, ข้อความตอบ)
6. **ผู้รายงานเห็นรายงานที่ตัวเองส่ง และสถานะของรายงาน**
7. **อาจารย์ผู้สอนวิชานั้นตรวจและตัดสินเอง** — ผลมีแค่ให้ blacklist (ยืนยัน) หรือไม่ให้ อาจารย์ **เห็นชื่อผู้รายงาน**
8. **เจ้าหน้าที่แค่รับรู้** ว่านักศึกษาคนไหนมี blacklist ติดอยู่ — ดูอย่างเดียว ไม่มีปุ่มตัดสิน
9. **คนโดนรายงานยื่นอุทธรณ์ได้** และ **อาจารย์คนเดิม** (ผู้สอนวิชานั้น) เป็นผู้พิจารณาอุทธรณ์
10. นอกจากนี้ "ที่เหลือตามที่เสนอ": รายงานที่ผู้รายงานถอนแล้ว **ยังนับเป็น 1 ใน 3**
11. **วิชาที่มี Lab Boy ไม่ถึง 3 คน (รวมตัวเอง) ปิดปุ่มรายงาน** — เพราะความลับผู้รายงานเป็นไปไม่ได้ (นับจากใบสมัคร accepted ไม่ยกเลิก ใน posting นั้น; server ตรวจซ้ำตอนส่ง) UI บอกเหตุผลที่ปิด
12. **คนโดนรายงานเห็นรายงานเฉพาะเมื่ออาจารย์ให้ blacklist แล้ว (CONFIRMED)** — ไม่เห็น/ไม่ได้แจ้งเตือนตอนส่ง, รายงานที่ถอนหรือไม่ผ่านจะไม่เห็นเลย, **ไม่มีการชี้แจงก่อนตัดสิน**; เมื่อเห็นแล้วยื่นอุทธรณ์ได้ทันที เวลาที่แสดงให้เขาเห็นเป็นระดับวัน (วันที่เกิดเหตุ/วันที่ตัดสิน) ไม่แสดงเวลาส่งรายงาน

## ไม่ทำ (Non-goals)

- ไม่ให้อาจารย์/เจ้าหน้าที่สร้างรายงานเอง
- เจ้าหน้าที่ไม่มีขั้นตอนตรวจ/อนุมัติใด ๆ
- blacklist ไม่ตัดสิทธิ์การสมัครอัตโนมัติ (คงหลักเดิมของระบบ)

## Anti-goals (ถ้าเกิดถือว่าล้มเหลว แม้ระบบจะทำงาน)

- คนโดนรายงานเดาได้ว่าใครรายงาน ผ่านช่องทางใดก็ตาม: ชื่อ/ID ใน JSON, `reporter_id`, ชื่อไฟล์หลักฐาน, `uploaded_by`, `author_id`, ประวัติสถานะ, ข้อความแจ้งเตือน, จำนวนโควตา/สถิติที่เปิดเผยต่อคนอื่น, หรือลำดับเวลาที่เปิดเผยละเอียดจนจับคู่ได้
- นักศึกษารายงานคนที่ไม่ได้อยู่วิชาเดียวกัน / รายงานตัวเอง / เกินโควตาได้ด้วยการยิง API ตรง
- อาจารย์วิชาอื่นตัดสินรายงานที่ไม่ใช่วิชาตัวเองได้

## สภาพปัจจุบัน (ที่ต้องรู้ก่อนลงมือ)

- Model: `models/labboy_report.go` — `LabBoyReport` (ApplicationID, StudentID, CourseID, ReporterID, status enum `DRAFT/SUBMITTED/UNDER_REVIEW/AWAITING_RESPONSE/CONFIRMED/NOT_SUBSTANTIATED/WITHDRAWN`, `ReconsiderationRequestedAt`) + ตาราง evidence / responses (`EXPLANATION/RECONSIDERATION/REPORTER_INFO`) / reviews / status_history; ทุกการเปลี่ยนสถานะเขียน `staff_audit_logs` ใน transaction เดียวกัน
- State machine: `reports/workflow.go` (`rules`, `CheckAction`, `CanView`, `ResponseKindFor`) — มี unit test `reports/workflow_test.go` และ integration test `reports/integration_test.go` (ต้องตั้ง `LABASSIST_TEST_MYSQL_DSN`)
- ซ่อนผู้รายงาน: `reports/anonymize.go` (`hidesReporter`, `anonymizeDetail`) — ปัจจุบันซ่อนจาก "นักศึกษาที่ไม่ใช่ผู้รายงาน"
- Blacklist ในระบบปัจจุบัน = รายงานสถานะ `CONFIRMED` (ตาราง `blacklists` เป็น legacy ไม่ใช้แล้ว) — อาจารย์วิชาอื่นเห็นผ่าน `ConfirmedHistory` (`/instructor/applications/:id/performance-records`, component `ConfirmedHistory.tsx` ใน `InstructorSelect.tsx`)
- รายวิชาที่ยืนยันตารางแล้วของนักศึกษา: `database.LabBoyAssignmentsForStudent` (`database/work_schedule.go`) — ใช้ซ้ำได้
- สิทธิ์อาจารย์ในวิชา: `database.InstructorOwnsCourse` (ตาราง `course_instructors`, source `imported`, ไม่ archived) — 1 วิชามีอาจารย์ได้หลายคน
- Frontend: `pages/student/StudentReports.tsx`, `pages/instructor/InstructorReports.tsx` + `InstructorReportCourse.tsx`, `pages/staff/StaffReports.tsx`, `pages/reports/ReportDetailPage.tsx`, `components/reports/*` (`ReportFormModal`, `ReportList`, …), เมนูใน `components/layout/Sidebar.tsx`

## ขั้นตอนใหม่ (State machine)

```
นักศึกษา A ส่งรายงาน B ──► SUBMITTED ──(อาจารย์: ให้ blacklist + เหตุผล)──► CONFIRMED
                              │   (B ยังไม่เห็นรายงานในช่วงนี้)                    │ B เห็นรายงาน + ยื่นอุทธรณ์ (1 ครั้ง)
                              │                                                  ▼
                              ├─(อาจารย์: ไม่ให้ blacklist + เหตุผล)──► NOT_SUBSTANTIATED
                              └─(A ถอน + เหตุผล)──► WITHDRAWN          CONFIRMED + อุทธรณ์ค้าง
                                                                        ├─ อาจารย์รับอุทธรณ์ → NOT_SUBSTANTIATED (ยก blacklist)
                                                                        └─ อาจารย์ยกอุทธรณ์ → คง CONFIRMED
```

- ส่งรายงานทันที ไม่มีร่าง (DRAFT) — การเดา: ร่างไม่จำเป็นสำหรับนักศึกษา และทำให้นับโควตาง่าย (ร่างไม่ใช่ "รายงาน")
- ผู้ตัดสินครั้งแรก = อาจารย์ผู้สอนคนใดก็ได้ของวิชานั้น (หรือ admin) — **การตัดสินใจของ Claude**; อุทธรณ์ดูหัวข้อ "การตัดสินใจของ Claude"
- ผู้รายงานถอนได้เฉพาะตอนยังไม่ตัดสิน (SUBMITTED)
- `UNDER_REVIEW` / `AWAITING_RESPONSE` ไม่ใช้ในขั้นตอนใหม่ (คง enum ไว้เพื่อข้อมูลเก่า)

## โควตา 3 ครั้ง

- นับ `labboy_reports` ที่ `reporter_id = ผู้รายงาน AND course_id = วิชานั้น` ทุกสถานะ (รวม WITHDRAWN)
- ต้องบังคับฝั่ง server ใน transaction เดียวกับ insert (กัน race สองคำขอพร้อมกัน — เช่น `SELECT ... FOR UPDATE` บนแถว application ของผู้รายงาน)
- UI แสดง "เหลือสิทธิ์รายงาน x จาก 3 ครั้ง" เฉพาะผู้รายงานเห็นของตัวเอง

## เงื่อนไขการรายงาน (server ตรวจทุกข้อ)

- ผู้รายงานมีใบสมัคร `accepted` ไม่ถูกยกเลิก ใน posting ที่ active + `lab_boy_schedule_confirmed`
- คนโดนรายงานมีใบสมัคร `accepted` ไม่ถูกยกเลิก ใน **posting เดียวกัน**
- ไม่ใช่ตัวเอง; client ส่งแค่ `application_id` ของคนโดนรายงาน — server เติม student/course/reporter เอง (แบบ `resolveApplication` เดิม)
- คงการกันรายงานซ้ำเดิม (ประเภทเดียวกัน/วันเดียวกัน/คนเดียวกัน)

## ใครเห็นอะไร

| ผู้ใช้ | เห็น |
|---|---|
| ผู้รายงาน (นักศึกษา) | รายงานที่ตัวเองส่ง + สถานะ + เหตุผลการตัดสิน |
| คนโดนรายงาน | เฉพาะรายงานที่ CONFIRMED (และผลอุทธรณ์ภายหลัง) โดย **ไม่มีข้อมูลผู้รายงาน** อุทธรณ์ได้ 1 ครั้ง |
| Lab Boy คนอื่น | ไม่เห็นรายงานใด ๆ ที่ตัวเองไม่ได้เกี่ยว |
| อาจารย์ผู้สอนวิชา | รายงานในวิชาของตน **รวมชื่อผู้รายงาน** + ปุ่มตัดสิน/พิจารณาอุทธรณ์ |
| เจ้าหน้าที่ | **รายชื่อนักศึกษาที่ติด blacklist อย่างเดียว** (ชื่อ, รหัสนักศึกษา, จำนวน blacklist — *จำนวนเป็นการตัดสินใจของ Claude*) — เปิดรายละเอียดรายงานไม่ได้ ต้องแคบ `CanView` ของ staff ลง |
| อาจารย์วิชาอื่น | ตอนคัดเลือกผู้สมัคร เห็นว่า **นักศึกษาคนนี้มี blacklist ติดตัว** (ป้าย + จำนวน) — ไม่เห็นรายละเอียด/ผู้รายงาน; `ConfirmedHistory` ที่แสดงรายละเอียดเดิมเปลี่ยนเป็นป้ายแทน (*การตีความของ Claude*) |
| admin | ทุกอย่าง |

## การตัดสินใจของ Claude (จาก builder check — เจ้าของตรวจได้)

- **อุทธรณ์ไปที่อาจารย์คนเดิม**: เก็บ `decided_by_id` ตอนตัดสิน; ปุ่มพิจารณาอุทธรณ์ให้เฉพาะคนนั้น ถ้าคนนั้นไม่ได้เป็นผู้สอนวิชานั้นแล้ว ให้อาจารย์ผู้สอนคนอื่นของวิชาพิจารณาแทน การตัดสิน/พิจารณาอุทธรณ์ทำได้แม้ posting ถูก archive แล้ว (เช็กจาก `course_instructors` ที่ไม่ archived ของวิชา ไม่ผูกกับ posting)
- **ไม่มี REOPEN** — ทางเดียวที่แก้ผลได้คืออุทธรณ์; อุทธรณ์ได้ **1 ครั้งตลอดชีวิตรายงาน** ใช้ flag ถาวร (ไม่ใช่ `ReconsiderationRequestedAt` ที่ถูกล้าง)
- **ผู้รายงานเห็น**: รายงานของตัวเอง สถานะ เหตุผลการตัดสิน และผลอุทธรณ์ — **ไม่เห็นคำชี้แจง/ข้อความอุทธรณ์** ของคนโดนรายงาน; แนบหลักฐานได้เฉพาะตอนส่ง; ตัด `REPORTER_INFO`
- **NOT_SUBSTANTIATED เป็นที่สุด**; รายงานคนเดิมซ้ำได้ (วันที่/ประเภทต่าง) ภายใต้โควตา 3 ครั้ง

## สิ่งที่ปล่อยให้ผู้สร้างตัดสินเอง

- โครงสร้างโค้ด: ปรับแพ็กเกจ `reports` เดิม (ใช้ตารางเดิม เปลี่ยนความหมาย ReporterID เป็นนักศึกษา) แทนการสร้างระบบใหม่
- หน้าตา UI ตามร่างใน `.superpowers/brainstorm/.../student-report-flow.html` และสไตล์ component เดิม
- ข้อความแจ้งเตือน (ห้ามมีชื่อผู้รายงานในแจ้งเตือนที่ส่งถึงคนโดนรายงาน)
- ข้อมูลรายงานเดิมของอาจารย์ในฐานข้อมูล (ปัจจุบันมีเพียงข้อมูล seed ทดสอบ) — ปรับ seed ให้เข้ากับขั้นตอนใหม่
